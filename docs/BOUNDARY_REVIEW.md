## 1. 结论与需要纠正的前提

项目已经确定“基于 dsh、固定其他条件、比较机制影响”和“两层评测”方向。本轮用户进一步确认首版以可复现的上下文机制研究实验为主要验收。尚未确定的是可归因的实验分组、资源公平性、任务边界以及外部复用深度。20 个待确认主题存在依赖，不能当作 20 个互不相关的选择。

社区已有 dsh 批量评测和消融项目。“社区缺少评测工具”不能作为已证实的立项依据。建议把本项目的价值聚焦到受控任务、明确的机制契约、预算计量、失败分类和配对分析；通用运行与报告能力优先审查是否可复用。该建议服务于已确认的机制研究验收目标，具体交付范围仍需收敛。

dsh 已有可替换的 compaction 服务，但“存在扩展点”不等于四种机制已能按实验协议接入。截断、历史检索、统一预算拦截和实际请求审计仍需兼容性验证。不得直接承诺无需任何适配就能运行。

## 4. 面向机制研究验收的可审查方案

首版验收中心已确认。以下交付形态、机制契约与协议仍是待确认方案，不能把 B-001 的答案扩展为对全部方案的认可。

### 4.1 交付与不纳入首版的能力

建议交付 dsh 机制插件、可脚本调用的实验入口、自建任务集、验证器、完整结果与 Markdown/JSON 报告。插件负责机制行为和事件；实验入口负责编排、隔离、预算与数据汇总。是否复用 dsh-eval 由兼容性检查决定。

Web 工作台、多 harness 排名、多模型全面评测、规划/反思/工具组织/子 Agent 机制对比、在线浏览任务和跨任务长期记忆不作为这条方案的首版验收要求。两层评测方向保留，外部层的首版深度仍由 B-005 决定。

### 4.2 四种上下文策略的候选契约

| 组 | 候选行为 | 需要冻结的参数或限制 |
| --- | --- | --- |
| Full History | 保留全部合法历史；不自动裁剪、摘要或检索。达到统一请求容量后结束该次运行，记录 `context_exhausted`。 | 请求容量包括固定提示、工具 schema、历史和输出预留；超限属于策略结果，不能被当成可忽略的基础设施错误。 |
| Truncation | 保留固定提示与任务约束，按完整工具调用/结果单元移除最早历史，保留可容纳的最近尾部。 | 明确保留的任务约束及尾部规则；不使用答案、标签或语义“重要性”挑选内容。单个不可拆单元超限的处理一致。 |
| Summary Only | 在冻结阈值处，用固定摘要提示压缩较旧历史，保留同一规则的近期尾部，不检索旧内容。 | 摘要模型、提示、输出上限、触发、失败与超限恢复规则；额外调用及 token 单独计量并计入资源预算。 |
| Summary + Retrieval | 使用相同摘要规则，在发送任务请求前按固定检索器取回本次会话的历史片段，装入固定检索额度。 | 语料只能含该次会话已经观察的历史；固定查询来源、分块、排序、去重与并列顺序。不允许访问参考答案、验证器或其他 trial。 |

四组结构不是摘要×检索的完整析因设计。Summary + Retrieval 与 Summary Only 的差异，只能说明在该摘要条件下加入检索的策略增益；不能据此宣布检索的独立主效应或二者交互效应。

检索额外占用有限窗口并可能挤占尾部；这属于实际策略的资源权衡。若要研究纯检索内容的贡献，需另加匹配 token 分配的对照。MVP 是否接受这一结论范围由 B-002 决定。

五组候选在上述四组之外增加 Retrieval Only：同一规则移除较旧历史，用同一检索器取回当前会话已观察的片段，不生成摘要。Truncation、Summary Only、Retrieval Only、Summary + Retrieval 分别对应摘要/检索的四种开关组合；Full History 为额外参考。独立贡献与交互分析要求四种组合共享明确的基础保留和资源分配规则，不能仅凭组名得出结论。固定任务数及重复数时，五组的 trial 数比四组增加 25%；实际费用取决于各组消耗。

### 4.3 实验协议必须覆盖的边界

| 边界 | 推荐处理 | 不这样处理会影响什么 |
| --- | --- | --- |
| 唯一变化项 | 固定模型路由、提示、工具、任务初态、采样参数和上游插件组合；只开放策略声明的字段。记录有效组合及实际请求。 | 名义上的单机制实验可能混入默认裁剪、提示注入或工具差异。 |
| 预算 | 区分单请求窗口、累计模型 token、输出上限、工具调用、时间与费用。辅助摘要调用纳入累计预算；检索本地开销单列。计数缺失为 `unknown`，不填 0。 | 资源不同或计量不完整时，不能得出同预算性能结论。 |
| 任务与工具环境 | “离线”指 Agent 的任务工具不依赖实时外部服务，模型 API 仍可联网。每个 trial 的文件与状态从相同初态启动。 | 在线变化与残留文件会污染配对比较。 |
| 主评分 | 自建主任务使用独立确定性验证器，核验产物和必要约束；验证器及答案不在 Agent 可读/可写范围内。过程指标单列。 | 运行结束、调用过工具或自称完成都不能证明任务成功。 |
| 失败 | 分开记录答案失败、上下文耗尽、策略失败、预算终止、用户取消和基础设施失败。超限、策略失败、预算终止保留在预定样本的报告中；基础设施缺失独立披露。 | 只统计完成样本会偏向更常终止的策略。 |
| 重试与续跑 | 基础设施重试记录原始尝试和已消耗资源，次数固定；不得因任务失败或低分选择性重试。续跑复用已验证完成的 trial，不把失败样本换成新样本后隐藏原结果。 | 报告会产生选择偏差或漏算费用。 |
| 配对与统计 | 按任务版本、初态和重复编号配对，策略执行顺序交错随机化。保留所有预定 trial，披露缺失；置信区间按独立任务/生成家族处理，不把同任务重复当成独立任务。 | 多次重复可能只扩大表面样本量；时间顺序可能混入服务负载。 |
| 任务压力与泄漏 | 在开发集调阈值，在冻结评测集报告。生成家族整体划分，避免近似变体跨集合。检查各策略实际触发与压力覆盖，同时报告低压力对照。 | 没触发的机制测不出差异；从评测结果倒推修改任务会使结论失真。 |
| 复现与回放 | 锁定 dsh、插件、任务、验证器、配置和环境版本/哈希；记录请求、上下文变化和资源来源。固定种子只能记录服务支持的部分；录制回放检验执行链，不替代新的模型实验。 | 不能把重复运行协议误称为模型输出逐字确定。 |
| 数据与报告 | 持久事件日志、请求上下文、产物和验证结果关联到 trial；过滤凭据。汇总成功率、资源、配对差异、失败类型与任务切片，保留基准原始分数定义。 | 截断展示轨迹无法解释上下文变化；不同基准的“分数”不能直接混合。 |

以上是协议建议；阈值、数值预算、重复次数和任务配比应在模型能力、费用及试跑计划明确后冻结，不能凭空认定足够。

## 6. 进入 SPEC 的条件

B-001 至 B-005 有明确答案或用户授权的有条件决定；可用模型、资源预算和验收环境已说明；机制与预算契约不存在冲突。依赖技术验证的事项必须写明验证产物、通过条件和失败时的替代方案，不能伪装成已经实现的能力。

之后按已有 D-007 顺序写 SPEC、PLAN、TASK，并把每项用户答案同步进 DECISIONS.md。尚未回答的事项保持为访谈底稿，不增加“已确认”决策。
